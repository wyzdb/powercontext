# 并行硬件与体系结构

## 弗林分类法：四种并行形态

按「指令流」和「数据流」两个维度，计算机被分成四类：

- **SISD**（单指令单数据）：传统单核顺序机，一条指令处理一份数据。
- **SIMD**（单指令多数据）：一条指令同时作用于多份数据。GPU 的 warp、CPU 的 AVX 向量指令都属于这一类。要害在「锁步」——所有通道执行同一条指令，只是数据不同。
- **MISD**（多指令单数据）：理论上存在，实用中几乎没有。流水线有时被勉强归进来。
- **MIMD**（多指令多数据）：每个处理单元有自己的指令流。多核 CPU、集群都属此类，是并行编程的主战场。

常见误区是把「多线程」当成 SIMD。多线程是 MIMD——每个线程可以走不同分支。SIMD 里一旦出现分支，硬件只能靠掩码把两条路径串行执行，这叫**分支发散**，是 GPU 性能的头号杀手。

判断口诀：看同一时刻所有执行单元是不是在跑同一条指令。是，就是 SIMD；各跑各的，就是 MIMD。

## 共享内存与分布式内存

两种物理模型决定了两种编程模型。

**共享内存**：所有核访问同一地址空间，靠 load/store 通信。通信是隐式的——写一个变量，别人读就到了。同步靠锁、原子操作、屏障。代表是 OpenMP、pthreads、C++ 的 std::thread。陷阱在于数据竞争不报错，只算出错结果；伪共享会让性能莫名其妙掉一半。

**分布式内存**：每个节点有自己的地址空间，谁也不能直接读别人的内存。通信是显式的——必须调用 send/recv 或集合通信。代表是 MPI。陷阱在于消息匹配错误会挂死而不是报错；通信和计算不重叠就是白等。

还有第三种——**分布式共享内存**（DSM/NUMA）：物理上分布式、逻辑上共享。它把两者的缺点也一并继承了：远程访问延迟高，但程序看起来仍像共享内存。

写代码前先问一句「这台机器的内存是共享的还是分布式的」，答案直接决定你该用 OpenMP 还是 MPI。

## 缓存一致性与伪共享

多核各自有 L1/L2 缓存，同一份数据可能有多份副本。缓存一致性协议（如 MESI）保证任何时刻所有核对同一地址的读写看到同一个值。

MESI 的四个状态：**M**odified（本核改过，别人都没有）、**E**xclusive（只有本核有且干净）、**S**hared（多核都有且干净）、**I**nvalid（已失效）。

关键机制：一个核要写某条缓存行，必须先让其他核的副本失效。这个「失效广播」就是代价所在。

**伪共享**（false sharing）：两个线程分别写两个不同的变量，但这两个变量恰好落在同一条缓存行（典型 64 字节）里。硬件按「行」而不是按「变量」维护一致性，于是两个线程互相把对方的缓存行打回 Invalid，写操作在总线上来回打架。

症状很有辨识度：逻辑上毫无共享的代码，多线程比单线程还慢，且随核数增加而恶化。

解法有两个：把热点变量按缓存行对齐并填充（padding 到 64 字节），或者让每个线程只写自己独立的一段数组。后者通常更简单。

## NUMA：距离开始变得重要

NUMA（非统一内存访问）机器上，每个 CPU 有自己的本地内存。访问本地内存快，访问别的 CPU 挂的内存慢，延迟通常差 1.5 到 3 倍。

Linux 上用 `numactl --hardware` 可以看到节点拓扑。默认分配策略是**首次触碰**（first touch）：哪个核先写某一页，页就分配在那个核的本地节点上。

这带来一个反直觉的后果：串行初始化一个数组、然后并行计算，会让所有页都落在 0 号节点的内存里，其他核全在做远程访问。

正确做法是用和计算相同的并行方式初始化——在 OpenMP 的 `parallel for` 里写 `a[i] = 0.0`，让页落在「将要使用它的核」的本地节点。

常见误判：在 NUMA 机器上测出扩展性差，往往不是算法问题，是内存摆放问题。先看 `numastat`，再怀疑代码。
