1我这轮的提示词
【目标】让混合检索真的跑起来，并且能证明「是数据库在干活」：
  1. 一条 SQL 同时完成 向量距离 + MATCH AGAINST 全文匹配 + 标量过滤
  2. 命中为空时能诚实降级，不许硬凑结果
  3. 命令行打印对齐表格：排名 / 融合分 / 出处
  4. 把这条 SQL 的 EXPLAIN 结果写进证据

【约束】
- 融合必须在一条 SQL 里完成，不要把候选集拉回 Python 再排序
- SQL 文本和参数分离（%(name)s 绑定），防注入
- query 做长度上限
- 每条命中必须带得出手的位置（source_file + heading_path），不然不给引用

【验收】Top1 出处正确；无关问题返回空；EXPLAIN 里能看到走了向量索引
2核心产出文件 · 一条 SQL 的三支结构
qoder/wengu/app/retrieval.py · SQL 常量150 行 · 入口 python -m app.retrieval
WITH vec AS (                              -- ① 向量支路：L2 距离 + ANN
  SELECT c.id, l2_distance(c.emb, %(qvec)s) AS dist
  FROM chunks c
  WHERE c.course = %(course)s
    AND c.review_status <> 'excluded'          -- ③ 标量过滤写在支路内部
    AND (%(topic)s IS NULL OR c.topic = %(topic)s)
    AND (%(level)s  IS NULL OR c.level  = %(level)s)
  ORDER BY dist APPROXIMATE LIMIT %(ncand)s   -- 走 HNSW，不是全表扫
),
ft AS (                                    -- ② 全文支路：ngram 自然语言模式
  SELECT c.id, MATCH(c.content) AGAINST(%(q)s) AS fts
  FROM chunks c
  WHERE MATCH(c.content) AGAINST(%(q)s)
    AND c.course = %(course)s AND ...同一组标量过滤...
  LIMIT %(ncand)s
),
vr AS (SELECT id, ROW_NUMBER() OVER (ORDER BY dist ASC)  AS rn FROM vec),
fr AS (SELECT id, ROW_NUMBER() OVER (ORDER BY fts DESC) AS rn FROM ft),
cand AS (SELECT id FROM vr UNION SELECT id FROM fr)   -- 两支取并集，谁掉队都能被拉回
SELECT c.id, c.doc_id, c.heading_path, c.topic, c.content,
       vr.rn AS vrank, fr.rn AS frank,
       -- ④ RRF 融合：1/(60+向量名次) + 1/(60+全文名次)，全程在 SQL 里
       COALESCE(1.0/(%(k)s + vr.rn), 0) + COALESCE(1.0/(%(k)s + fr.rn), 0) AS fused
FROM cand
LEFT JOIN vr ON vr.id = cand.id
LEFT JOIN fr ON fr.id = cand.id
JOIN chunks c ON c.id = cand.id
ORDER BY fused DESC, c.id ASC
LIMIT %(k_limit)s
阈值与「拒绝编造」判据retrieval.py:22-45
K = 60       # RRF 平滑常数
NCAND = 40    # 每支召回宽度
FUSED_FLOOR = 0.0099  # ≈ 1/(60+40+1)
# 为什么不是 0.0164：单支路排第 1 名也只有
# 0.01639，阈值再高会把「只有一支命中」全丢掉

def coverage(query, content) -> float:
    """向量支路永远返回 ncand 条，所以「融合分」
    判断不了「资料里到底有没有」。
    覆盖率才可以：问语料里没有的话题时，
    查询的 bigram 基本不会出现在正文里。"""
    grams = [g for g in _grams(query) if g not in STOP_GRAMS]
    return sum(1 for g in grams if g in content) / len(grams)
# 只当闸门（< 0.25 判未命中），不参与重排——
# 字面指标一去排序会打乱语义向量排好的顺序

EXPLAIN SELECT c.id, l2_distance(c.emb, ?) d
  FROM chunks c
 WHERE c.course = ? AND c.review_status <> ?
 ORDER BY d APPROXIMATE LIMIT 5;

|--|----------------------------------------|----------------------|--------|------------|
|0 |VECTOR INDEX ADAPTIVE SCAN (PRE-FILTER)|c(idx_course_doctype)|12     |491       |

两个关键点：
1. 算子名里就是 VECTOR INDEX —— 没退化成全表扫描
2. PRE-FILTER：标量过滤先在 course 索引上砍到 12 行，
   再进 HNSW。这就是「过滤必须写进支路内部」的原因

担心的 CTE 退化并不存在：把同样的 ANN 包进 WITH，
计划里仍是这个算子 → 融合可以留在 SQL 里。

4本轮踩坑与遗留
  • 占位符只能用 %(name)s：pymysql 不认 ?。 SQL 文本与参数始终分离，问题原文进 AGAINST(%(q)s) 不会被拼进语句。
  • BOOLEAN MODE 中文恒为 0：见第 3 轮，自然语言模式是唯一选择，已写进 §4.10。
  • 「资料里有没有」不能靠融合分：ANN 支路无论问什么都会填满 40 条候选，于是加了 bigram 覆盖率闸门 + 停用词表（什么/怎么/为何…），否则问「红烧肉」也会一本正经地引用缓存一致性。
  • 遗留（不掩饰）：① ft 支路目前是 LIMIT 而没有 ORDER BY fts DESC，全文名次取自未排序的截取，语料一大就会抖；② 提示词里要求的 qa_log 落库尚未接（今日实测 0 行），CLI 入口改成模块自带 python -m app.retrieval；③ has_code / concept 两个过滤参数还没暴露到 search() 签名，第 7 轮出题要用。
