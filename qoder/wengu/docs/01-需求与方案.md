## 0. 语料勘察结论

数字取自 `data/manifest.json`（由 `scripts/build_manifest.py` 生成）：

| 文件 | 主题 | 节数 | 字数 |
|---|---|---|---|
| `01-architecture.md` | 弗林分类、共享/分布式内存、MESI 与伪共享、NUMA | 4 | 1717 |
| `02-performance.md` | 加速比、Amdahl、Gustafson、强/弱扩展 | 4 | 1626 |
| `03-mpi-basics.md` | 通信子、消息匹配、四类死锁、非阻塞 | 4 | 2728 |
| `04-collectives.md` | Bcast/Scatter/Gather、Reduce、树形通信、误用 | 4 | 2143 |
| `05-openmp.md` | fork-join、数据作用域、竞争、调度 | 4 | 2789 |
| `06-design.md` | Foster 四步法、分解模式、计算强度 | 3 | 1696 |

合计 6 篇 / 23 节 / 12699 字 / 约 29 块。

**主题是一条线，不是六个孤岛**：硬件形态 → 性能怎么量 → 进程间怎么通信（点对点）→ 群体怎么通信（集合）→ 线程怎么共享内存 → 算法怎么设计。这条线决定了 §4.9 的前置依赖边是有依据的，不是随手连的。

**概念重叠**：§4.8 的 40 个概念里有 13 个跨篇出现，其中五个出现 3 篇以上：

| 概念 | 覆盖篇数 | 意味着什么 |
|---|---|---|
| `measure-first` 先测量再优化 | 4 | 贯穿全部六讲的主张，适合做跨章串讲的第一题 |
| `shared-vs-distributed` 共享/分布式内存 | 3 | 所有编程模型选择的前提 |
| `false-sharing` 伪共享 | 3 | 体系结构、性能、OpenMP 三处都能考 |
| `sync-primitives` atomic/critical/barrier | 3 | 同步手段的选型题 |
| `load-balance` 负载均衡 | 3 | 分解与调度的交汇点 |

这些跨篇概念是出题的富矿：一个概念在多篇里出现，说明它既能单独考、也能做辨析题。

**规模判断：29 块属于小语料**，这直接决定了两个设计选择。

1. **出处必须精确到「文件 + 小节」**。29 块里靠相似度挑前 5，若不带出处，用户无法判断该不该信。所以 `chunks.heading_path` 是一等公民，不是装饰。
2. **差异化不能押在「检索得更全」上**。语料就这么点，检索上限肉眼可见。真正能拉开差距的是「记得住这个人哪里不会」——这就是 PowerContext 的位置，也是整个项目的支点。

**三处语料硬伤**（已在 2026-10-28 直接修正，详见 §4.6 的修订记录）：Amdahl 表格数值、Allreduce 通信量口径、`MPI_SUM` 大小写。三条都不是排版问题，是会在讲解时**教错人**的实质错误。

这件事本身说明了产品判断：语料错误必须落到数据模型上（`review_status`），不能靠「以后注意」。

## 1. 用户与场景

**谁**：用公开讲义自学并行计算的人。典型是三类——备考研究生课程的在读生、转行做 HPC 的工程师、准备 MPI/OpenMP 面试题的人。

不针对某个具体班级，因为语料本身就是公开讲义，谁都能拿到同一份。

**什么时候**：考前三天；面试前一周；刚读完一章，想确认自己到底掌握没有。

**现在怎么做**（三步，每一步都在漏）：

1. 打开 6 个 markdown，在编辑器里全局搜关键词。搜到了，但搜出来的是三行长句，看不出这句是不是答案。
2. 翻到那一节，从头读到尾，合上。第二天忘掉 70%。
3. 做错一道题，心里记一下「这个我错了」。下次还是错同一类，因为没东西提醒。

**痛在哪**（按强度排序）：

| # | 痛点 | 具体表现 |
|---|---|---|
| 1 | 找得到，但不知道哪条是重点 | 23 节里任何一节都可能考，判断依据在脑子里，不在资料里 |
| 2 | 错了没人记 | 错题本要手抄，抄完不看，下次重犯 |
| 3 | 不知道从哪开始 | 剩三天，六篇，先看哪篇？凭感觉抽一篇，往往不是最该看的那篇 |

**量化目标**（第 8 轮验证样例要能对上这几个数）：

- 一次定位：从提问到拿到带出处的答案 **< 10 秒**（现状是翻 3–5 分钟）
- 一次复习：今日清单 3 个概念 + 3 道题，**15 分钟做得完**
- 记忆留存：同一概念错满 3 次后，系统**必须优先再考它**，而不是随机抽题

## 2. 功能边界

**做四件事**，每件都能落到 §4.3 的映射表上：

1. **导库** —— 一条命令把 `data/raw/` 的 markdown 变成可检索的块。增量靠 `src_mtime` + `content_sha` 双判据（mtime 相同但内容变了也要重导）。
2. **带出处的问答** —— 一条 SQL 完成向量 + 全文 + 标量过滤，返回的每一段都带 `source_file` 和 `heading_path`。资料里没有就直说没有。
3. **弱点驱动出题与判分** —— 从 PowerContext 读弱点选概念，从 `chunks` 取该概念的依据块出题，判分后把结果写回记忆。
4. **今日复习清单** —— 3 个概念 + 3 道题 + 预计耗时，15 分钟能做完。

**不做什么**（每条都写理由，不是懒得做）：

| 不做 | 理由 |
|---|---|
| 多用户与权限体系 | 单机单人使用。评审要的是「跑得起来、看得懂」，不是一个 SaaS 后台 |
| 文档上传界面 | 语料固定 6 篇，加文件只需丢进 `data/raw/` 重跑脚本。做上传 UI 是纯成本，还会引入解析失败的支路 |
| 切换 embedding 模型 | 维度一改就要全库重建，收益是「可能更准一点」，风险和成本都不划算。维度写死在 `kb_meta.embed_dim` 里 |
| 通用 RAG 平台 | 一旦往通用做，复习闭环这个核心就被摊薄了。这个项目的卖点是「记得你」，不是「什么都能问」 |
| 移动端 / 部署到云 | 演示和评审都在桌面。部署复杂度换不来分 |

边界的一句话总结：**凡是不能落到「哪张表 / 哪个端点」的功能，一律砍掉**（§4.3 已逐条核对过）。

## 3. 技术分工表

| 组件 | 存什么 / 查什么 | 不做什么 | 证据落点 |
|---|---|---|---|
| **seekdb** | 存 9 张表：文档状态、切片正文与向量、概念词表、概念关系、题目、答题记录、查询日志。查：一条 SQL 完成向量 + 全文 + 标量过滤的融合排序 | 不存用户状态（弱点、进度、偏好）。这类数据没有向量、没有全文检索需求，放进来只会让备份和迁移变复杂 | §4.2 建表、§4.4 混合检索、`qa_log` |
| **PowerContext** | 存每个学习者一个 scope 的 `weakness` / `progress` / `preference`。查：出题前的弱点排序、判分后的写回、跨会话的画像 | 不存文档正文、不存向量、不做全文检索。它不是数据库，是上下文服务 | §4.7 scope 粒度与 4 个函数契约 |
| **LLM**（`deepseek-chat`） | 出题、判分、讲解 | 不负责检索、不负责记忆。检索结果由 SQL 给出，记忆由 PC 给出，LLM 只做语言层 | §4.7.3 |
| **Qoder** | 开发工具，不参与运行时 | — | `docs/00-Qoder提示词脚本.md` 的八轮记录 |

**一句话分工**：seekdb 记得「资料说了什么」，PowerContext 记得「你哪里不会」。

这两句话不能互换——把弱点塞进 seekdb，就丢了「跨会话自动召回」的能力；把文档塞进 PC，就丢了混合检索。**分工互斥才立得住**。

## 4. 数据模型

### 4.0 设计与验收约束

| 约束 | 在模型里的落点 |
|---|---|
| 向量 + 全文 + 标量过滤在**一条 SQL** 内完成 | `chunks` 表同时持有 `emb VECTOR(1024)`、`content_seg`（全文索引列）、`course/topic/level/has_code/doc_type`（标量过滤列）；见 §4.4 的可执行 SQL |
| seekdb 是唯一数据存储 | 9 张表全部落在 seekdb，无 SQLite / Redis / 本地 JSON 状态文件。`data/ingest_report.json` 等属于**报告产物**，不是存储，不作为任何功能的读取源 |
| PowerContext 是唯一记忆存储 | 学习者专属的可变状态（弱点、进度、偏好）只写在 PC，seekdb 里没有任何 per-learner 状态列 |
| 向量维度从 `.env` 读 | DDL 写死字面量 `1024`；`kb_meta.embed_dim` 存权威值；ingest 启动时三方比对（`.env` ↔ `kb_meta` ↔ 实际返回维度），不一致直接退出，见 §4.5 |
| 记忆必须显式写入 | §4.7 的 4 个客户端函数由判分流程**主动**调用；没有任何依赖模型自动抽取的路径 |
| 禁止触碰 `data/local/` | 模型中不存在指向该目录的列、路径常量或种子数据；`doc_meta.source_file` 的取值域被 `data/raw/%` 前缀约束（见 §4.3 CHECK 说明） |
| 密钥只读 `.env` | 表结构不含任何凭据列；PC 的 token 只在请求头，日志表不落 token |

**字段约定（全库统一）**

- 字符集：`utf8mb4` / `utf8mb4_general_ci`；索引列长度均 ≤ 191，避免前缀索引退化。
- 时间：`DATETIME(0)` 存本地时区（`+08:00`），由应用层统一转换；不用 `TIMESTAMP` 以规避 2038 与时区隐式转换。
- 布尔：`TINYINT(1) NOT NULL DEFAULT 0`，取值 0/1，不允许 NULL（NULL 会让 `%(has_code)s IS NULL OR ...` 这类过滤分支变成三值逻辑陷阱）。
- 枚举一律 `ENUM`，不用自由字符串——自由值是后续迁移之坑的源头。
- 所有外键用 `RESTRICT`，删除语料只允许走 `--rebuild` 整表重建，不允许级联静默删除。

### 4.1 表清单与建表顺序

库名 `wengu`。建表按依赖顺序执行，**整段可直接粘贴运行**：

| # | 表 | 角色 | 服务哪个功能 |
|---|---|---|---|
| 1 | `kb_meta` | 单行/键值元信息（schema 版本、embedding 模型与维度） | 全部功能的启动自检 |
| 2 | `doc_meta` | 文档级状态（篇、节数、mtime、内容指纹） | F-导入：增量与幂等 |
| 3 | `chunks` | 切片正文 + 向量 + 全文 + 标量 | F-问答、F-出题依据 |
| 4 | `concept` | 受控词表：概念规范化（别名归一） | F-出题、F-写回去重 |
| 5 | `chunk_concept` | 切片 ↔ 概念 多对多 | F-出题（concept → 依据段落）、重叠统计 |
| 6 | `concept_edge` | 概念前置依赖 / 辨析关系 | F-复习顺序推荐 |
| 7 | `quiz_item` | 题目本体 + 答案键 + 依据切片 | F-出题、F-判分 |
| 8 | `qa_log` | 检索事件流（append-only） | 证据与统计，**不参与决策** |
| 9 | `quiz_attempt` | 判分事件流（append-only） | 证据与统计，**不参与决策** |

「不参与决策」是硬规定：F-复习清单 / F-出题选题**只读 PC**，不许回头聚合 `qa_log`/`quiz_attempt` 来推断弱点。否则记忆状态就分裂在两个系统里，跨会话可证性（第 5 轮验收点）立刻失效。这条边界的完整论证见 §3（待补）。

### 4.2 建表 SQL

```sql
-- ============================================================
-- 000 库与元信息
-- ============================================================
CREATE DATABASE IF NOT EXISTS wengu
  DEFAULT CHARACTER SET utf8mb4 DEFAULT COLLATE utf8mb4_general_ci;
USE wengu;

-- 键值元信息。权威维度/模型/版本只认这张表，改模型不改代码只改数据是不允许的。
CREATE TABLE kb_meta (
  k            VARCHAR(64)  NOT NULL,
  v            VARCHAR(255) NOT NULL,
  updated_at   DATETIME(0)  NOT NULL,
  PRIMARY KEY (k)
) ORGANIZATION=HEAP;

INSERT INTO kb_meta (k, v, updated_at) VALUES
  ('schema_version',          '1',            NOW()),
  ('embed_model',             'text-embedding-v3', NOW()),
  ('embed_dim',               '1024',         NOW()),
  ('chunker_version',         'h2-v1',        NOW()),
  ('fulltext_parser',         'ngram',        NOW()),
  ('corpus_root',             'data/raw',     NOW()),
  ('corpus_manifest_sha',     '',             NOW());


-- ============================================================
-- 010 文档级状态
-- ============================================================
CREATE TABLE doc_meta (
  doc_id          VARCHAR(64)  NOT NULL COMMENT 'front matter: doc_id',
  title           VARCHAR(200) NOT NULL,
  source_file     VARCHAR(255) NOT NULL COMMENT '恒以 data/raw/ 开头，禁止 data/local/',
  course          VARCHAR(64)  NOT NULL,
  doc_type        VARCHAR(32)  NOT NULL COMMENT '讲义/习题/教材节选(本期只用讲义)',
  language        VARCHAR(8)   NOT NULL DEFAULT 'zh',
  front_matter    JSON         NULL COMMENT '原样留档，排查切片争议用，不作检索',
  char_len        INT UNSIGNED NOT NULL DEFAULT 0,
  cjk_len         INT UNSIGNED NOT NULL DEFAULT 0,
  section_count   SMALLINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '## 小节数',
  chunk_count     SMALLINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '实际入库块数，含二次切分',
  src_mtime       DATETIME(0)  NOT NULL COMMENT '增量判断：文件修改时间',
  content_sha     CHAR(40)     NOT NULL COMMENT 'sha1(正文)，mtime 相同但内容变了的兜底',
  ingest_status   ENUM('pending','indexed','failed','stale') NOT NULL DEFAULT 'pending',
  last_indexed_at DATETIME(0)  NULL,
  error_note      VARCHAR(500) NOT NULL DEFAULT '',
  created_at      DATETIME(0)  NOT NULL,
  updated_at      DATETIME(0)  NOT NULL,
  PRIMARY KEY (doc_id),
  UNIQUE KEY uk_doc_source (source_file),
  KEY idx_doc_status (ingest_status, course),
  KEY idx_doc_mtime  (src_mtime)
) ORGANIZATION=HEAP;


-- ============================================================
-- 020 切片：混合检索主表
-- ============================================================
CREATE TABLE chunks (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  chunk_uid     CHAR(40)        NOT NULL COMMENT 'sha1(source_file|section_no|part_no)，幂等唯一键',
  doc_id        VARCHAR(64)     NOT NULL,
  source_file   VARCHAR(255)    NOT NULL,
  section_no    SMALLINT UNSIGNED NOT NULL COMMENT '第几个 ## 小节，1 起',
  section_heading VARCHAR(200)  NOT NULL COMMENT '小节标题原文',
  heading_path  VARCHAR(300)    NOT NULL COMMENT '《标题》>> 小节名 >> (第 i/j 段)，直接用于引用展示',
  part_no       TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '超长节的二次切分序号',
  part_count    TINYINT UNSIGNED NOT NULL DEFAULT 1,
  content       MEDIUMTEXT      NOT NULL COMMENT '切片正文，返回给 LLM 的就是这一列',
  content_seg   MEDIUMTEXT      NOT NULL COMMENT '与 content 等义的预分词文本(空格分隔)，全文索引列',
  char_len      INT UNSIGNED    NOT NULL,
  -- 标量过滤列：一条 SQL 里的 WHERE 全靠它们
  course        VARCHAR(64)     NOT NULL,
  doc_type      VARCHAR(32)     NOT NULL,
  language      VARCHAR(8)      NOT NULL DEFAULT 'zh',
  topic         ENUM('architecture','performance','mpi','openmp','design') NOT NULL,
  level         ENUM('入门','进阶') NOT NULL,
  has_code      TINYINT(1)      NOT NULL DEFAULT 0,
  formula_keys  VARCHAR(255)    NOT NULL DEFAULT '' COMMENT '逗号分隔，如 amdahl,speedup；空串表示无公式',
  -- 语料质量标记：讲义自带错误靠它拦住，见 §4.6
  review_status ENUM('ok','suspect','excluded') NOT NULL DEFAULT 'ok',
  review_note   VARCHAR(255)    NOT NULL DEFAULT '',
  -- 向量列：维度写死 1024，与 kb_meta.embed_dim 双向校验
  emb           VECTOR(1024)    NOT NULL,
  src_mtime     DATETIME(0)     NOT NULL,
  ingested_at   DATETIME(0)     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_chunk_uid (chunk_uid),
  KEY idx_topic_level_code (topic, level, has_code),
  KEY idx_course_doctype   (course, doc_type),
  KEY idx_doc_section      (doc_id, section_no, part_no),
  KEY idx_review           (review_status),
  KEY idx_src_file         (source_file, src_mtime),
  FULLTEXT INDEX idx_chunks_ft (content) WITH PARSER ngram,
  VECTOR INDEX idx_chunks_emb (emb)
      WITH (distance=l2, type=hnsw, lib=vsag, m=16, ef_construction=200, ef_search=64)
) ORGANIZATION=HEAP;


-- ============================================================
-- 030 受控词表：概念
-- ============================================================
CREATE TABLE concept (
  concept_id     VARCHAR(48)  NOT NULL COMMENT 'kebab-case slug，如 false-sharing',
  canonical_name VARCHAR(96)  NOT NULL,
  aliases        VARCHAR(512) NOT NULL DEFAULT '' COMMENT '逗号分隔，中英混排："伪共享,false sharing,MESI 误触发"',
  topic          ENUM('architecture','performance','mpi','openmp','design') NOT NULL,
  docs_span      VARCHAR(128) NOT NULL DEFAULT '' COMMENT '出现该概念的 doc_id 列表，冗余出来便于人工核对重叠',
  doc_count      TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '跨了几篇；>1 即概念重叠，见 §0',
  note           VARCHAR(255) NOT NULL DEFAULT '',
  PRIMARY KEY (concept_id),
  UNIQUE KEY uk_concept_name (canonical_name),
  KEY idx_concept_topic (topic, doc_count)
) ORGANIZATION=HEAP;


-- ============================================================
-- 040 切片 ↔ 概念
-- ============================================================
CREATE TABLE chunk_concept (
  chunk_id    BIGINT UNSIGNED NOT NULL,
  concept_id  VARCHAR(48)     NOT NULL,
  role        ENUM('primary','mention') NOT NULL DEFAULT 'mention'
              COMMENT 'primary=该节主讲它；mention=顺带提到。出题只允许 primary 块当答案依据',
  PRIMARY KEY (chunk_id, concept_id),
  KEY idx_cc_concept (concept_id, role, chunk_id),
  CONSTRAINT fk_cc_chunk   FOREIGN KEY (chunk_id)   REFERENCES chunks(id)   ON DELETE RESTRICT,
  CONSTRAINT fk_cc_concept FOREIGN KEY (concept_id) REFERENCES concept(concept_id) ON DELETE RESTRICT
) ORGANIZATION=HEAP;


-- ============================================================
-- 050 概念关系：前置依赖与辨析
-- ============================================================
CREATE TABLE concept_edge (
  from_id    VARCHAR(48)  NOT NULL COMMENT '依赖方向：学 from 之前先懂 to',
  to_id      VARCHAR(48)  NOT NULL,
  edge_type  ENUM('requires','contrasts','part_of') NOT NULL,
  rationale  VARCHAR(255) NOT NULL DEFAULT '' COMMENT '一句话依据，附讲义出处，防止依赖图靠猜',
  PRIMARY KEY (from_id, to_id, edge_type),
  KEY idx_edge_to (to_id, edge_type),
  CONSTRAINT fk_edge_from FOREIGN KEY (from_id) REFERENCES concept(concept_id) ON DELETE RESTRICT,
  CONSTRAINT fk_edge_to   FOREIGN KEY (to_id)   REFERENCES concept(concept_id) ON DELETE RESTRICT
) ORGANIZATION=HEAP;


-- ============================================================
-- 060 题目本体
-- ============================================================
CREATE TABLE quiz_item (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  item_uid      CHAR(40)        NOT NULL COMMENT 'sha1(concept_id|kind|stem)，去重新题不重复入库',
  concept_id    VARCHAR(48)     NOT NULL COMMENT '考点，必须已在 concept 注册',
  kind          ENUM('choice','calc','judge','short','code_review') NOT NULL,
```

### 4.4 一条 SQL 完成混合检索

用到哪些列，逐条对上：

- **向量支路**：`chunks.emb`（`l2_distance` + `APPROXIMATE` 走 `idx_chunks_emb`）
- **全文支路**：`chunks.content_seg`（`MATCH ... AGAINST` 走 `idx_chunks_ft`）
- **标量过滤**：`chunks.course`、`chunks.topic`、`chunks.level`、`chunks.has_code`、`chunks.doc_type`、`chunks.review_status`，可选 JOIN `chunk_concept.concept_id`
- **融合**：RRF，`1/(60+rank)` 两支路相加，`k=60` 固定写死，不做成参数（可调即不可复现）

```sql
-- 命名参数由 pymysql 侧传值，SQL 文本永不拼接
WITH vec AS (
  SELECT c.id, l2_distance(c.emb, %(qvec)s) AS dist
  FROM chunks c
  WHERE c.course = %(course)s
    AND (%(topic)s IS NULL     OR c.topic = %(topic)s)
    AND (%(level)s IS NULL     OR c.level = %(level)s)
    AND (%(has_code)s IS NULL  OR c.has_code = %(has_code)s)
    AND (%(concept)s = ''       OR c.id IN (
            SELECT cc.chunk_id FROM chunk_concept cc
            WHERE cc.concept_id = %(concept)s AND cc.role = 'primary'))
    AND c.review_status <> 'excluded'
  ORDER BY dist APPROXIMATE LIMIT %(ncand)s
),
ft AS (
  SELECT c.id, MATCH(c.content) AGAINST(%(qseg)s) AS fts
  FROM chunks c
  WHERE MATCH(c.content) AGAINST(%(qseg)s)
    AND c.course = %(course)s
    AND (%(topic)s IS NULL     OR c.topic = %(topic)s)
    AND (%(level)s IS NULL     OR c.level = %(level)s)
    AND (%(has_code)s IS NULL  OR c.has_code = %(has_code)s)
    AND (%(concept)s = ''       OR c.id IN (
            SELECT cc.chunk_id FROM chunk_concept cc
            WHERE cc.concept_id = %(concept)s AND cc.role = 'primary'))
    AND c.review_status <> 'excluded'
),
vr AS (SELECT id, ROW_NUMBER() OVER (ORDER BY dist ASC)  AS rn FROM vec),
fr AS (SELECT id, ROW_NUMBER() OVER (ORDER BY fts DESC) AS rn FROM ft),
cand AS (SELECT id FROM vr UNION SELECT id FROM fr)
SELECT
  c.id, c.doc_id, c.source_file, c.heading_path, c.topic, c.level,
  c.review_status, c.review_note,
  vr.rn AS vrank, fr.rn AS frank,
  COALESCE(1.0/(60 + vr.rn), 0) + COALESCE(1.0/(60 + fr.rn), 0) AS fused,
  LEFT(c.content, 300) AS preview
FROM cand
LEFT JOIN vr ON vr.id = cand.id
LEFT JOIN fr ON fr.id = cand.id
LEFT JOIN chunks c ON c.id = cand.id
ORDER BY fused DESC, c.id ASC
LIMIT %(k)s;
```

三个必须守住的正确性要点（第 4 轮拿 EXPLAIN 证明）：

1. **标量过滤必须写在两个支路子查询内部**。写在外层会让 ANN 分支退化成全表扫描，融合就失去意义——这正是「一条 SQL」这个选型理由的实现细节。
2. **两支路候选量 `%(ncand)s` 取 40**（`k=5` 的 8 倍）。太小会在语料只有 29 块时出现两支路重叠率过高、融合分区分度不足；太大则 RRF 尾部噪声进入排序。
3. **命中阈值**：`fused < 0.0099`（≈ `1/(60+ncand+1)`，ncand=40 时为 `1/101`）判为未命中，走 `degraded='empty'` 且 `answered=0`，回答固定为「资料中未提及」。
   阈值**不能**取 `1/61=0.01639` 或更高：单支路排第 1 名也得 `0.01639`，一旦阈值 ≥ 0.0164，单支路命中会被全部丢弃，只剩两路同时命中的结果，看起来就是「问什么都说不了解」。这条是 §6 风险清单里"小语料假命中"的落点。

降级路径：`MATCH ... AGAINST` 报错（分词器不可用）时，同一条 SQL 去掉 `ft`/`fr` 两支，只留 vec，并置 `degraded='vector_only'`——不许改成 Python 里排序融合。

### 4.5 中文全文索引：定稿方案与两条退路

**主方案**：`FULLTEXT INDEX idx_chunks_ft (content_seg) WITH PARSER ngram`，`ngram_token_size = 2`。

- `content_seg` 由 ingest 写入：与 `content` 同行、同语义，中文按二分词（bigram）以空格连接，ASCII 标识符（`MPI_Allreduce`、`firstprivate`）保留原样并追加一份小写形态，公式名保留 `formula_keys` 里的 slug。
- 检索侧 `%(qseg)s` **必须用同一个分词函数**生成，否则查询词与索引词不同源，命中率归零。
- 双列同时存在的理由：`content` 是返回给 LLM 与展示的唯一正文，不能被空格污染；`content_seg` 只做索引。二者由同一切片派生，`char_len` 只记 `content`。

**退路 A（parser 名不被接受，报 `syntax error near 'WITH PARSER'`）**：去掉 `WITH PARSER ngram`，索引仍建在 `content_seg`（已预分词，默认 parser 按空格切即可命中），代价是需要 `innodb_ft_min_token_size <= 2`。若该参数无权限调整，退路 B 接手。

**退路 B（默认 parser + min_token_size 卡在 3）**：ingest 改为对 `content_seg` 每个 token 追加填充至 4 字符（`伪|默` 形态，由同一函数在查询侧对称还原）。这是纯字符串技巧，不引入新依赖，不改表结构。

**定稿判据**（写进第 3 轮验收，不允许"看起来能查"）：

```sql
-- 建完表立刻跑，命中数 > 0 才算过
SELECT COUNT(*) AS hit FROM chunks
WHERE MATCH(content_seg) AGAINST('伪共享' IN BOOLEAN MODE);
-- 期望 >= 2（01-architecture 与 05-openmp 各至少一块）
```

跑完把实际生效的 parser 名回写：`UPDATE kb_meta SET v='ngram|default|padded', updated_at=NOW() WHERE k='fulltext_parser';` —— 检索层启动时读这一行决定 `%(qseg)s` 用哪个分词函数。三种取值都对应代码里的一条确定分支，不留待会再问。

### 4.6 语料质量标记（`review_status`）的初始落库

逐篇核对 23 节时核实到 3 处缺陷。**语料是应用唯一的事实来源，带着错误进检索就会教错学习者**，所以模型层面必须有落点，而不是"以后人工注意"。已用公式复核：

| # | 位置 | 问题 | 复核 | 定级 |
|---|---|---|---|---|
| D1 | `02-performance.md` 第 2 节《Amdahl 定律》表格 | `s=5%` 在 `p=8` 时写 4.7，按 `S=1/(s+(1-s)/p)` 应为 **5.93**；4.7 是 `s=10%` 那行的值被复制。紧随其后的「5% 和 10% 在 8 核时差别不大」因此不成立（5.93 vs 4.71 差 26%） | `1/(0.05+0.95/8)=5.926`、`1/(0.10+0.90/8)=4.706` | `suspect` |
| D2 | `04-collectives.md` 第 4 节《常见误用》第 4 条 | `Allreduce ≈ 2·(p−1)/p·n` 代入 `n=1MB, p=1024` 得 **约 2.0 MB**（单进程量），文中结论写「搬 2 GB」。2 GB 只在把 1024 个进程的量**聚合**时成立，口径未标注 | `2*1023/1024*1MB=1.998MB`；`×1024≈2.0GB` | `suspect` |
| D3 | `04-collectives.md` 第 2 节《归约与 Allreduce》 | 文中写 `MPI_Sum`，标准接口名是 `MPI_SUM`（全大写）。大小写敏感的答案比对会把它判成错的 | — | `suspect` |

**语料已在 2026-10-28 直接修正**（时间戳见 `data/manifest.json` 的 `generated_at`），当前不存在 `suspect` 块，9 张表里 `chunks.review_status` 的初始值全部为 `ok`。

下面三条保留为**修订记录**，不再作为落库动作执行；仅当语料回退到旧版本、重跑 ingest 后需要重新定位时，按此表对照：

| # | 定位 | 原值 | 修正为 |
|---|---|---|---|
| D1 | `02-performance.md` 第 2 节《Amdahl 定律》表格 | `s=5%`、`p=8` → 4.7 | 5.9 |
| D2 | `04-collectives.md` 第 4 节《常见误用》第 4 条 | 「搬 2 GB」未标口径 | 「单进程约 2 MB，全进程合计约 2 GB」 |
| D3 | `04-collectives.md` 第 2 节《归约与 Allreduce》 | `MPI_Sum` | `MPI_SUM` |

三条使用规则，写死在读取逻辑里：

- **检索/讲解**：`suspect` 块照常返回，`review_note` 必须原样透传到前端与 LLM 上下文，讲解时先说「讲义此处数值存疑，按公式推导应为 …」。
- **出题**：`basis_chunk_ids` 命中任一 `review_status='suspect'` 的块时，该题 `answerable=0`，选题 SQL 只取 `answerable=1`。计算题**永不**以 `suspect` 块为依据。
- **`excluded`** 保留给后续人工判定完全不可用的块：检索层默认过滤掉，且过滤写进两支路内部（§4.4 要点 1）。

D1–D3 同时也是 §0 语料勘察的产出物，等 §0 补齐时把这 3 条列进勘察结论。

### 4.7 PowerContext 侧：scope 粒度与记忆条目

#### 4.7.1 scope 粒度

| 决定 | 内容 | 理由 |
|---|---|---|
| 粒度 | **一个学习者一个 scope**，`learner:<handle>` | 记忆读取永远是「这个人全部档案」或「这个人 + 某概念」，没有跨 learner 的合法查询；拆到 `learner:<id>%(course)s:<c>` 会让「换课程」变成 scope 迁移，白白多出一次搬迁 |
| handle 规则 | `^[a-z0-9][a-z0-9_-]{0,31}$`，用户自取，服务端与客户端双重校验 | 挡住「拿姓名+学号当 handle」；演示固定用 `demo`、`newbie` |
| 多课程 | 同 scope 内靠 `concept_id`（天然带 topic）与条目里的 `course` 字段区分，**不新建 scope** | 见上 |
| 一个 scope 内放几类记忆 | 三类混放，用 `type` 区分：`weakness` / `progress` / `preference` | 读档案要一次拿全，分 scope 会把一次 profile 变成三次网络往返 |
| 幂等键 | `key` 字段：`weakness:<concept_id>`、`progress:<concept_id>`、`preference:<slot>` | 同一概念重复错只 `count+1`，不新增条目（第 5 轮验收点） |
| 归属 | 记忆内容**只**存 PC。seekdb 里除 `quiz_attempt.memory_ref`（一个 UUID 指针）外，没有任何学习者状态 | 状态分裂 = 跨会话不可证 |

PC **不存**：切片正文、讲义原文、embedding、题目文本。`evidence.basis` 只存**出处指针**（`source_file` + `heading_path` + `chunk_id`），正文靠 `chunk_id` 回 seekdb 表取。这条规则保证「既存文档又存记忆」的灰地带不存在：原文永远只在 seekdb，判断永远只在 PC。

#### 4.7.3 四个客户端函数 ↔ 端点契约

函数签名固定（第 5 轮实现 `app/memory.py` 就是这四个，不增不改）：

| 函数 | 语义 | HTTP 契约 |
|---|---|---|
| `get_profile(learner)` | 读 scope 内全部 weakness + progress + preference | `GET {PC_BASE_URL}/scopes/learner:{h}/memories?type=weakness` 等三次读取合并，`type` 缺省 = 全读 |
| `upsert_weakness(learner, concept, wrong_answer)` | 先按 `key` 查，命中 → `count+1`、`status` 回退 `新学`、刷新 `last_seen`；未命中 → 新建 `count=1` | 读：`GET .../memories?key=weakness:{c}`；写：`POST .../memories`；改：`PUT .../memories/{id}` |
| `advance_progress(learner, concept)` | `streak_correct+1`，跨档则升 `status` | 同上 `PUT` |
| `get_review_plan(learner, days)` | 读 weakness，按 `count × 时间衰减` 排序，`days` 只影响衰减窗口 | `GET` + 本地纯计算；**不新增端点** |

路径字符串的**唯一真相**放在 `app/memory.py` 顶部的 4 个常量里。第 2 轮 `smoke_test.py` 的职责就是把这 4 条逐个探测到 2xx；若实际路径不同，只改这 4 个常量，数据结构、函数签名、表结构一律不动。这条设计把「PC 端点未知」的风险限制在 4 行常量内（详见 §6 风险 R1）。

失败语义（写死，不许即兴发挥）：

| 情况 | 返回 | 上层动作 |
|---|---|---|
| 网络失败 | 重试 3 次（指数退避 0.5/1/2s） | 仍失败 → 抛 `MemoryUnavailable` |

### 4.10 实测校正（seekdb V1.4.0，2026-10-28）

以下结论来自真实数据库，不是推断。环境：`oceanbase/seekdb:latest`（容器 819 MB），端口 2881，MySQL 协议。

**建表**：§4.2 的 12 条语句（1 建库 + 1 USE + 1 初始化 INSERT + 9 张表）**全部成功**，包括内联 `VECTOR INDEX` 与 `WITH PARSER ngram`。

**向量索引参数**：A / B / C 三档全部可建，`M`、`EF_CONSTRUCTION`、`EF_SEARCH` 均被接受。§4.2 用 A 档保守写法即可，不必降级。

**ANN 执行计划**：`ORDER BY l2_distance(...) APPROXIMATE LIMIT` 包在 CTE 里**依然走向量索引**，计划中出现 `VECTOR INDEX ADAPTIVE SCAN (PRE-FILTER)`。§4.4 的 CTE 写法可用，R8 风险解除。

**两个必须改的实现细节**（已同步到 §4.2 与 §4.4）：

1. **`IN BOOLEAN MODE` 不能用于中文 ngram 查询。** 实测：

   | 索引 | 查询串 | 自然语言 | 布尔 |
   |---|---|---|---|
   | 原文 + ngram | `伪共享` | **1** | 0 |
   | 原文 + ngram | `伪共 共享` | 1 | 1 |
   | bigram + space | 两种都试 | 0 | 0 |

   布尔模式不会把查询串切成 bigram，整串「伪共享」在索引里不存在，所以命中 0。要么用自然语言模式，要么在查询侧显式切成「伪共 共享」再走布尔模式。

2. **`content_seg` 这一列取消。** ngram 分词器直接作用于原文即可（`TOKENIZE('伪共享指两个线程','ngram')` 返回 `["伪共","共享","享指","指两","两个","线..]`，切分正确）。预分词后再交给 ngram 是双重分词，只会引入不一致。

   同时排除另一条路：`WITH PARSER space` + bigram 预分词**不可行**——SPACE 分词器默认 `min_token_size=3`，两字 bigram 会被全部丢弃，索引为空。

**因此 §4.5 的分词方案作废，改为**：

- `chunks.content` 直接建 `FULLTEXT INDEX ... WITH PARSER ngram`
- ingest 不再生成 bigram 文本，少一处可能与检索侧不一致的实现
- 检索侧 `MATCH(content) AGAINST(%(q)s)`，自然语言模式
- 若日后需要「必须包含某词」的精确语义，再在查询侧做 bigram 切分并切回布尔模式，两处必须同源

**PowerContext 端点实测更正（2026-10-28）**：§4.7.3 表格里的 `/scopes/{scope}/memories` 等路径是推测值，服务起来后核对发现真实 API 是 `/v1/memory/remember`、`/v1/memory/entries/list`、`/v1/context/prepare`，请求体字段为 `text` + `kind`（不是 `content`），且 scope 由服务端生成、不能自带。`app/memory.py` 已按真实端点重写，4 个常量的隔离设计奏效——只改了这一个文件，数据结构与上层逻辑未动。

**验证脚本**：`tools/verify_ddl.py`（建表）、`tools/probe_vector.py`（向量索引三档 + EXPLAIN）、`tools/probe_fulltext.py`（分词与命中率对照）。三个脚本都在真实库上跑过，输出见 `docs/03-实测记录.md`。

## 5. 主流程时序

```text
① 导入（一次性 + 增量）
   data/raw/*.md
     → 解析 front matter（doc_id / doc_type / course）
     → 按 "##" 切块，超长节二次切分
     → 生成 content_seg（bigram 分词版）
     → 调 embedding（1024 维）
     → 写 chunks / concept / chunk_concept
     → 更新 doc_meta.ingest_status = 'indexed'

② 提问
   前端 → POST /api/ask {learner, query}
     → retrieval.hybrid_search()  一条 SQL：向量 + 全文 + 过滤，RRF 融合
     → 返回 chunks（含 heading_path）
     → LLM 带 [1][2] 引用作答
     → 写 qa_log（query, top_ids, latency_ms, degraded）

③ 出题
   GET /api/today/{learner}
     → PowerContext 读 weakness，按 count × 时间衰减排序
     → 取 top3 概念
     → chunk_concept 取 role='primary' 的依据块
     → 写 quiz_item（answerable=1，basis_chunk_ids 指回出处）

④ 判分
   前端 → POST /api/grade {learner, attempt}
     → 读 quiz_item.answer_key / rubric_points
     → 选择题比对；简答题 LLM 打分 + 理由
     → 写 quiz_attempt
     → 答错：PC upsert_weakness(count+1, status 回退"新学")
       答对：PC advance_progress(streak+1，跨档则升级)

⑤ 下次会话（跨进程）
   新进程启动 → get_profile(learner)
     → 弱点仍在 → 今日清单随之变化
```

数据在哪一步流经谁，一眼能看出来：**① 只碰 seekdb，③⑤ 只碰 PowerContext，②④ 两边都碰**。

第 2 步和第 4 步是全流程唯一两处「两个组件同时在场」的地方，也是技术结合真正的落点：

- ② 用 seekdb 找依据、LLM 生成回答，把这次提问记进 `qa_log`
- ④ 用 PowerContext 决定考什么、用 seekdb 提供答案依据、把结果写回 PowerContext

一句话概括整条链：**资料在 seekdb 里不动，人的状态在 PowerContext 里累积；每次交互都是「读记忆 → 查资料 → 写记忆」。**
