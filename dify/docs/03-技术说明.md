# 技术说明

> 一句话：**牌由确定性引擎打，话由 LLM 说，事由 seekdb 和 PowerContext 记。**

---

## 1. 为什么这么分工

斗地主是强规则游戏（14 种牌型、带牌、顺子长度、炸弹压制）。把出牌交给 LLM，必然出现非法牌和漏牌，评审上手第一分钟就会卡住。

所以本作把"规则"和"表达"彻底分开：

| 层 | 由谁负责 | 做不好会怎样 |
|---|---|---|
| 规则（发牌、判定、胜负、步数） | Python 引擎，跑在 Dify 的代码节点里 | 交给模型 → 出非法牌 |
| 表达（台词、解说、心理战） | LLM（qwen-plus） | 交给规则引擎 → 台词僵硬 |
| 检索（残局讲解、牌型速查） | seekdb + Dify 知识库 | 没有 → 提示无依据 |
| 记忆（卡关、战绩、旧账） | PowerContext | 没有 → 换个会话就失忆 |

---

## 2. Dify 承担了什么

应用的完整流程是一张 14 节点的 Chatflow，全部编排在 Dify 内：

| 节点 | 类型 | 作用 |
|---|---|---|
| 开始 | start | 接收玩家输入与可选的玩家 ID |
| 身份 | 代码执行 | 生成存档 key（`ddz-<玩家ID>`） |
| 取存档 | HTTP 请求 | `POST /v1/scopes`，幂等创建玩家 scope |
| 解析存档 | 代码执行 | 从响应 JSON 取 `scope_id` |
| 引擎 | 代码执行 | **核心**：牌型判定、AI 出牌、胜负、步数（783 行） |
| 写回 | 变量赋值 | 把 `state` / `level` 写回会话变量 |
| 召回记忆 | HTTP 请求 | `POST /v1/context/prepare` |
| 解析记忆 | 代码执行 | 剥离 PowerContext 的固定前缀，只留记忆正文 |
| 讲解 | 知识检索 | 从 seekdb 知识库取残局讲解（TopK 2） |
| 对白 | LLM | qwen-plus 生成老K/小七台词，不碰牌 |
| 过滤台词 | 代码执行 | 两人关（无右家）时剔除"小七"的台词 |
| 是否结算 | 条件分支 | `settled == true` 时写记忆 |
| 写记忆 | HTTP 请求 | `POST /v1/memory/remember` |
| 输出 / 直接回复 | 模板 + 回复 | 牌桌 + 台词合并输出 |

**规则引擎为什么放在代码节点**：这样"Dify 承担核心编排"是字面成立的——出牌判定发生在 Dify 的节点里，不是外部后端。引擎源码同时保留在仓库 `engine/doudizhu.py`，可独立单测（20 条测试全过）。

## 3. seekdb 承担了什么

| 项 | 配置 |
|---|---|
| 用途 | Dify 知识库的**向量存储** |
| Dify 配置 | `VECTOR_STORE=oceanbase`、`OCEANBASE_VECTOR_HOST=seekdb` |
| 容器 | `quay.io/oceanbase/seekdb:latest`，端口 2881 |
| 数据 | 3 个文档 → 1 张向量表 → 36 条向量 |

验证记录：

```sql
-- evidence/01-seekdb-tables.png
SHOW TABLES;
-- vector_index_8aec1085_23b5_426d_9964_407efdfc0b13_node

-- evidence/02-seekdb-count.png
SELECT COUNT(*) FROM vector_index_8aec1085_23b5_426d_9964_407efdfc0b13_node;
-- 36
```

### 适配补丁（重要）

Dify 1.9.1 的 OceanBase 适配层与 seekdb 不兼容，会直接导致建库失败：

```
File ".../oceanbase_vector.py", line 86, in _create_collection
    val = int(row[6])
ValueError: invalid literal for int() with base 10: 'CLUSTER'
```

原因：`SHOW PARAMETERS` 的第 6 列是 `value`，代码却取了第 7 列（`info`），seekdb 在该位置返回 `'CLUSTER'`。

修复（`deploy/patched/oceanbase_vector.py`）：

1. 依次尝试第 6/5/4/7/3 列，取第一个可转整数的值
2. 参数不存在时降级为告警，不再抛异常
3. `ALTER SYSTEM SET` 失败时降级为告警

挂载方式见 `deploy/docker-compose.patch.yaml`（只覆盖 api / worker / worker_beat 三个容器）。

## 4. PowerContext 承担了什么

| 项 | 设计 |
|---|---|
| 粒度 | **每个玩家一个 scope**，`idempotency_key = ddz-<玩家ID>` |
| 写入时机 | 每关结算（通关/失败）写一条 `event` |
| 记忆正文 | `第 1 关 · 顺子开路：通关（2 步预算，用了 2 步）` |
| 读取时机 | 每回合 `prepare_context`，query = 玩家输入 + 当前关卡名 |
| 读取方式 | 显式 API，不依赖模型自动抽取 → 结果确定、可复现 |
| 跨会话 | 新会话 `game_state` 为空，但 scope 不变 → 记忆仍在 |

**为什么不用自动抽取**：比赛要求"评审可按步骤复现"，模型自动抽取有时间延迟和不确定性；显式写入让每次结算都能立刻在 Dashboard 看到。

## 5. 一轮对话的时序

```
玩家输入 "3 3"
  → 身份：player_key = ddz-lxz
  → 取存档：POST /v1/scopes（幂等，返回同一个 scope_id）
  → 引擎：读 game_state → 判定 33 可出 → 清空手牌 → status=win
  → 写回：game_state / level 更新
  → 召回：POST /v1/context/prepare，取回"上回第1关…"
  → 讲解：seekdb 知识库检索（TopK 2）
  → 对白：qwen-plus 生成 2-3 句台词（不得改牌）
  → 过滤：两人关剔除小七
  → 是否结算：settled=true
  → 写记忆：POST /v1/memory/remember
  → 输出：牌桌 + 台词
```

## 6. 实现中踩到的坑（可复现记录）

| # | 现象 | 原因 | 处理 |
|---|---|---|---|
| 1 | `Output message is missing` | 界面上的代码节点**没有真正保存**，服务端 `code length` 为 0 | 改为通过控制台 API 写入草稿 |
| 2 | `items.0.operation 枚举不匹配` | Dify 的赋值节点枚举是 `over-write`，不是 `overwrite` | 改为 `over-write` |
| 3 | 条件分支后面的节点不执行 | if-else 的两个分支句柄是 `true` / `false`，不是 `source` | 修正 sourceHandle |
| 4 | 回复显示 `tpl01.text` | 模板转换节点的输出变量名是 `output`，不是 `text` | 改为 `{{#tpl01.output#}}` |
| 5 | 建知识库报 `int('CLUSTER')` | Dify 的 OceanBase 适配层取错列 | 见第 3 节补丁 |
| 6 | 记忆召回了但模型不提 | 记忆放在 system 提示里被当噪音 | 挪到 user 消息 + 硬性句式要求 |

> 这些不是"环境问题"，是 Dify 1.9.1 与 seekdb 联调时的真实适配工作，补丁与脚本都在仓库里。

## 8. 已知限制

1. **单机演示**：PowerContext 未开鉴权，靠内网/本机访问；公网部署需改 `ACCESS_MODE=enforced` 并加 token。
2. **残局模式**：只做残局，不含发牌、叫地主、倍数、春天。
3. **AI 水平**：引擎里的对手是启发式（最小合法牌 + 快输时压大），不是强 AI。
4. **记忆粒度**：按关卡结算写入，不记录每一手牌；因此"读心"体现在战绩与关卡，而非逐手风格。
5. **知识库规模**：3 个文档、36 条向量，够演示，不构成完整牌谱库。
6. **会话变量**：牌局状态存在 Dify 会话变量里，新会话即重开第 1 关（记忆跨会话，牌局不跨）。
